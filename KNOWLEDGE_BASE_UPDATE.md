# Инструкция по обновлению базы знаний
## Vassian FAQ/RAG Assistant

## 1. Что входит в базу знаний

Основные файлы находятся в каталоге `data/`.

### FAQ

`data/faqs.json`

Используется для структурированных пар:

```json
{
  "question": "Вопрос",
  "answer": "Подтверждённый ответ"
}
```

### Информация о специалисте

`data/about_me.txt`

Содержит подтверждённую информацию о специализации, компетенциях и других фактах, которые разрешено использовать в ответах.

### Услуги и условия работы

`data/services.txt`

Содержит:

- список услуг;
- порядок работы;
- правила формирования стоимости;
- общую схему оплаты;
- информацию о сроках;
- сведения о сопровождении.

### Кейсы

`data/cases/*.txt`

Каждый кейс хранится отдельным текстовым файлом.

### Неподтверждённая информация

`NEEDS_CONFIRMATION.md`

Этот файл используется как список сведений, которые требуют проверки. Такие сведения не следует переносить в рабочую базу знаний до подтверждения.

## 2. Основное правило обновления

В базу знаний добавляются только факты, которые можно подтвердить.

Нельзя добавлять:

- предположения;
- приблизительные цены, если они не утверждены;
- придуманные сроки;
- незафиксированные гарантии;
- технологии, которые «скорее всего использовались»;
- рекламные утверждения без фактического основания.

Если факт вызывает сомнение, сначала поместить его в `NEEDS_CONFIRMATION.md`.

## 3. Обновление FAQ

1. Открыть `data/faqs.json`.
2. Добавить или изменить объект с `question` и `answer`.
3. Проверить валидность JSON.
4. Сохранить файл в UTF-8.
5. Пересобрать FAISS-индекс.
6. Выполнить тестирование.

Пример:

```json
{
  "question": "Можно ли начать с небольшой задачи?",
  "answer": "Да. Возможность начать с ограниченного объёма обсуждается отдельно."
}
```

## 4. Обновление текстовых документов

Для изменения профиля или услуг:

1. отредактировать соответствующий `.txt`;
2. не менять подтверждённый смысл ради более привлекательной формулировки;
3. сохранить файл в UTF-8;
4. пересобрать индекс.

## 5. Добавление нового кейса

1. Создать новый файл:

```text
data/cases/new_case_name.txt
```

2. Указать только подтверждённые сведения:

- название;
- задача;
- реализованное решение;
- использованные технологии;
- результат — только если он реально подтверждён.

3. Сохранить файл.
4. Пересобрать индекс.
5. Проверить запросы к новому кейсу и уточняющие вопросы.

## 6. Пересборка FAISS-индекса

Из корня проекта, в активированном виртуальном окружении:

```bash
python -m backend.build_index
```

Скрипт:

1. читает `faqs.json`;
2. читает текстовые документы из `data/`;
3. читает кейсы из `data/cases/`;
4. нормализует документы;
5. получает embeddings через текущий `AIProvider`;
6. создаёт новый FAISS-индекс;
7. сохраняет индекс и metadata.

Для реальной пересборки нужны корректные настройки AI-провайдера в `.env`.

Пересборка не запускается автоматически при импорте модуля или старте приложения.

## 7. Файлы индекса

Рабочая конфигурация использует два связанных артефакта:

- FAISS index;
- metadata.

В текущем репозитории это:

```text
data/faiss_index.bin
data/faqs_metadata.npy
```

Их нужно обновлять согласованно после изменения базы знаний.

## 8. Проверка после обновления

Сначала выполнить автоматические тесты:

```bash
python -m pytest tests/ -v
```

Затем провести несколько ручных проверок:

1. прямой вопрос по изменённому факту;
2. перефразированный вопрос;
3. уточняющий follow-up;
4. вопрос, на который ответа по-прежнему нет;
5. запрос на выдуманную цену/срок/гарантию;
6. prompt-injection тест.

Для полной проверки использовать `PROMPT_TEST_CASES.md`.

## 9. Проверка API

После развёртывания:

```text
GET /health
```

Ожидается:

- статус API `ok`;
- признак наличия FAISS-индекса.

После этого проверить `POST /chat` через веб-виджет или API.

## 10. Безопасное обновление production

Рекомендуемый порядок:

1. изменить исходные документы локально;
2. проверить diff;
3. пересобрать индекс;
4. запустить тесты;
5. вручную проверить критические prompt-cases;
6. только затем обновить production;
7. после обновления проверить `/health`;
8. сделать несколько реальных запросов через сайт.

## 11. Когда нужно менять системный промпт

Системный промпт не следует менять при каждом обновлении фактов.

**Менять базу знаний**, если изменились:

- услуги;
- кейсы;
- контакты;
- условия работы;
- подтверждённые факты.

**Менять системный промпт**, если изменились:

- роль ассистента;
- правила допустимого поведения;
- правила эскалации;
- стиль;
- требования безопасности;
- политика работы с неизвестной информацией.

Так факты и правила остаются разделены, а система проще поддерживается.
