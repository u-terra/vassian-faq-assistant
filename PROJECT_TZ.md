# Техническое задание
## ИИ FAQ/RAG-ассистент для сайта vassian.ru

**Тип проекта:** реальный проект коммерческого назначения  
**Назначение:** поддержка посетителей сайта и первичная консультация по услугам, кейсам и условиям работы  
**Интерфейс:** веб-виджет на сайте vassian.ru  
**Backend:** FastAPI  
**RAG:** FAISS  
**Память диалога:** SQLite по `session_id`  
**AI-провайдер:** Yandex AI Studio через абстракцию `AIProvider`

## 1. Цель проекта

Разработать ИИ-ассистента для сайта vassian.ru, который отвечает посетителям на типовые вопросы об услугах, реализованных проектах, формате сотрудничества и контактах, используя только подтверждённую базу знаний.

Ассистент должен сокращать объём ручных ответов на повторяющиеся вопросы и помогать посетителю быстро понять, какие задачи можно решить и как перейти к дальнейшему обсуждению проекта.

## 2. Бизнес-задачи

Проект должен:

- автоматизировать ответы на частые вопросы посетителей;
- обеспечивать первичную консультацию без постоянного участия человека;
- уменьшать риск противоречивых или выдуманных ответов;
- сохранять контекст многоходового диалога;
- помогать посетителю перейти от общего вопроса к предметному обсуждению задачи;
- работать непосредственно на сайте.

## 3. Пользовательские сценарии

Ассистент должен корректно обрабатывать следующие классы запросов:

1. Вопросы об услугах.
2. Вопросы о чат-ботах и AI-ассистентах.
3. Вопросы об автоматизации бизнес-процессов.
4. Вопросы о сайтах и используемых технологиях.
5. Вопросы о реализованных кейсах.
6. Вопросы о стоимости, сроках и порядке работы.
7. Вопросы о сопровождении после запуска.
8. Запрос контактной информации.
9. Уточняющие вопросы, зависящие от предыдущей реплики.
10. Вопросы, на которые в базе знаний нет подтверждённого ответа.
11. Попытки получить внутренние инструкции или заставить ассистента игнорировать ограничения.

## 4. Функциональные требования

### 4.1. Системный промпт

Системный промпт должен определять:

- роль ассистента;
- его назначение;
- источник допустимых фактов;
- стиль общения;
- правила поведения при отсутствии данных;
- запрет на выдумывание цен, сроков, гарантий, технологий и результатов;
- правила работы с историей диалога;
- запрет на раскрытие системных инструкций и внутренних технических данных.

### 4.2. База знаний

Ассистент использует структурированную базу знаний проекта:

- `data/faqs.json` — FAQ;
- `data/about_me.txt` — подтверждённая информация о специалисте;
- `data/services.txt` — услуги, порядок работы, стоимость, оплата, сроки и сопровождение;
- `data/cases/*.txt` — описания реализованных кейсов;
- `NEEDS_CONFIRMATION.md` — вопросы и сведения, которые нельзя считать подтверждёнными и включать в ответы как факты.

### 4.3. RAG-поиск

Система должна:

- преобразовывать документы базы знаний в embeddings;
- хранить векторный индекс в FAISS;
- получать релевантные фрагменты для текущего вопроса;
- передавать найденный контекст в модель вместе с системными инструкциями;
- отделять retrieval от генерации ответа.

### 4.4. Контекст диалога

Для каждой сессии должна сохраняться история сообщений.

Требования:

- идентификатор сессии — `session_id`;
- история хранится в SQLite;
- в промпт передаётся ограниченное число последних сообщений;
- для уточняющего вопроса retrieval-запрос учитывает предыдущий пользовательский вопрос;
- сгенерированный ранее ответ ассистента не должен использоваться как источник фактов для retrieval.

### 4.5. Работа при отсутствии информации

Если подтверждённых данных нет, ассистент должен:

1. прямо сообщить, что точной информации нет;
2. не заполнять пробелы общими знаниями модели;
3. не придумывать факты;
4. предложить связаться напрямую для уточнения, если это уместно.

### 4.6. Веб-интеграция

Должны быть доступны:

- `GET /health` для проверки состояния API;
- `POST /chat` для диалога;
- самостоятельный веб-виджет;
- вариант встраивания виджета в сайт на Tilda;
- production-развёртывание по HTTPS.

### 4.7. Независимость от конкретной LLM

Работа приложения не должна быть жёстко связана с SDK одного AI-провайдера.

В проекте используется интерфейс `AIProvider` с операциями:

- получение embeddings;
- генерация ответа.

Текущая реализация работает через Yandex AI Studio. Архитектура допускает добавление другого провайдера без переписывания основной логики приложения.

## 5. Нефункциональные требования

- Ответы — преимущественно на русском языке.
- Стиль — естественный, спокойный, профессиональный, без избыточной рекламы.
- Ответы должны быть краткими и релевантными вопросу.
- Секреты и API-ключи не хранятся в репозитории.
- Тесты не должны требовать реальных ключей AI-провайдера.
- Отсутствие FAISS-индекса не должно приводить к аварийному завершению API.
- Пользователю не должен возвращаться внутренний RAG-контекст.

## 6. Критерии приёмки

Проект считается выполненным, если:

- ассистент доступен через сайт;
- API отвечает и создаёт/продолжает пользовательскую сессию;
- база знаний индексируется в FAISS;
- ответы формируются на основе retrieved-контекста;
- история диалога учитывается;
- уточняющие вопросы сохраняют смысл предыдущего пользовательского запроса;
- при отсутствии данных ассистент не выдумывает ответ;
- системный промпт содержит явные ограничения;
- внутренняя реализация не раскрывается в обычном ответе;
- предусмотрена процедура обновления базы знаний;
- основные компоненты покрыты автоматическими тестами;
- проект и его логика документированы.

## 7. Результат

Работающий FAQ/RAG-ассистент опубликован на сайте vassian.ru и используется как демонстрационный и портфельный пример практического применения промт-инжиниринга, RAG, контекстного диалога и интеграции LLM в веб-приложение.
